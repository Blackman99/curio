What is this?

A toy theatre in a pop-up book, played by the scroll bar. Toy theatres were the sheets of scenery and characters sold in Regency and Victorian London, "a penny plain and twopence coloured" as Stevenson put it in his 1884 essay, cut out and stood up on card. This one is printed as a 90° pop-up. Every flat, cloth, wave, the curtain and the camera are CSS @keyframes animations whose clock is the stage's scroll position (animation-timeline: --book, a scroll timeline). Each part owns a slice of the scroll bar through animation-range: the storm cloth flies in over 33–39%, the lightning lives at 45, 52.5 and 58.5%. That is 35 scroll-driven animations in 15 cues, and no JavaScript animation; the paper slips that drift past use view() timelines of their own.

Why do it in CSS? Chrome runs scroll-driven animations of transform and opacity on the compositor thread, the thread that also does the scrolling. Freeze JavaScript runs a busy loop, so no script, scroll event or animation frame can run. The understudy at the top right has the same DOM and the same keyframes, moved the classic way: a scroll listener sets each animation's currentTime. It stops dead, and so does the JS clock.

Measured in Chrome 147 on an Apple M4 Pro GPU, from the frames the compositor actually sent (a DevTools screencast; screenshots wait for the main thread, so they can't see this). A 3.0 s freeze with a glide: 265 frames went out, showing 56 different pictures of the big stage and 52 of the ribbon; the understudy, the page number and the JS clock showed 1 each. A wheel gesture already under way kept scrolling right through the freeze: 3,066 px, 246 different pictures of the big stage, 2 of the understudy. Chrome logged each freeze as one long animation frame of about 3,014 ms. With the fallback forced (?nosda), all 257 frames showed the same picture.

Not everything on a scroll timeline is free. The page number on the ribbon is a scroll-driven animation too, of a registered custom property feeding a CSS counter. Only the main thread can draw that, so it froze for the whole freeze while the ribbon next to it kept growing.

What I couldn't show. A wheel gesture that starts during the freeze: headless Chrome's synthetic input waits for the main thread, so I couldn't measure that case. The Freeze button therefore starts a smooth scroll just before it stops the main thread, so there is always something to watch. In the software renderer the frames arrived about a second late and the counts were muddled, so the numbers above are from the GPU only.

Support (MDN, 5 Nov 2026): Chrome and Edge 115, Safari 26, Firefox 159 (released 27 October 2026). Without it, the page detects CSS.supports('animation-timeline: scroll()') and moves both stages from the scroll listener, so the play still runs, and a freeze stops both. Tested: Playwright's WebKit 26.4 plays it natively (it can't draw the custom-property page number, so that tag is hidden), Firefox 148 runs the fallback, both without errors. Spec: CSS Scroll-driven Animations; MDN. Every piece of scenery is SVG drawn in the page.
